# Backend (FastAPI)

Owned by house-template-fastapi. Sources: the FastAPI docs (https://fastapi.tiangolo.com/), RFC 9457 (https://www.rfc-editor.org/rfc/rfc9457), the pydantic-settings docs (https://docs.pydantic.dev/latest/concepts/pydantic_settings/), the LangChain and LangSmith docs (https://docs.langchain.com/) and pytest-recording (https://github.com/kiwicom/pytest-recording).

- The import package is `app` under `backend/src/`; the app is built by `app.main.create_app`. Process-long resources (database engine, model clients) open and close in `lifespan`, never at import time.
- Authentication: protect routes with `app.auth.CurrentUser` (or `OptionalUser`). Replace `app.auth.authenticate` with the project's real verification (session or bearer token, checked against the provider); until then production answers 401 everywhere, and `X-Dev-User` stands in for a user locally and in tests only. `User.id` is the provider's opaque subject, never an email; scope every owned row and query to it.
- API conventions: product routes live in `app/api/` and join `app.api.router` (mounted at `/v1`); a breaking change goes to a new `/v2` router beside it. Each route declares its return type (a Pydantic model, never an ORM object), protects itself with `CurrentUser`, and scopes queries to the user. List endpoints take `PageParamsDep` and return `Page[T]` built with `page()`: keyset (cursor) pagination, never offsets. `app/api/__init__.py` shows a whole resource.
- Dependencies use `Annotated[T, Depends(...)]` aliases. Settings come only from `app.settings.get_settings()` (tests pass a `Settings` to `create_app`); secrets are `SecretStr`, and every new setting goes in `backend/.env.example` with a safe value.
- Errors are RFC 9457 problem details: raise `app.problems.Problem(status, detail=..., headers=...)` for expected failures (`Retry-After` on a 503 or 429). Model provider failures are already mapped (busy 503, timeout 504, input too long 422, unreachable 502, misconfigured 503, with `Retry-After` where retrying helps); storage raises 400 for a bad key and 404 for a missing file. Never put submitted values, secrets or stack traces in an error body; unexpected errors are logged with the request id and return a bare 500.
- Every request logs one `request` line (method, route template, status, duration, request id), and library logs (uvicorn, SQLAlchemy, LangChain) go through the same renderer, so production logs are JSON throughout. Log with `structlog.get_logger()` and keyword fields (`log.info("course_imported", course_id=...)`), never f-strings, and never log secrets or personal data.
- Readiness checks are registered with `app.health.add_readiness_check`; `/health/live` never touches a dependency.
- Production: the app refuses to start with `APP_ENV=production` on the local default database URL or storage key. Every connection has a statement timeout (30 s) and an idle-in-transaction timeout (60 s); commit or close a session before a long wait (a model call), and never hold a transaction across one. Migrations give up after waiting 5 s for a lock. CORS is off until `CORS_ORIGINS` lists the frontends; set `ALLOWED_HOSTS` in production. Responses carry nosniff, frame-deny, no-referrer and (unless a route sets its own) `Cache-Control: no-store`.
- Database: SQLAlchemy 2.1 async with psycopg 3. Inject `app.db.SessionDep`, commit explicitly, load relationships with `selectinload()` and declare them `lazy="raise"`. Models subclass `app.db.Base` and are imported in `app/models.py`.
- Migrations have two branches: the template's (`template`, arriving with template updates) and the project's (`app`). `make migration` writes on `app`; `make migrate` and the migrate job run `alembic upgrade heads`. Never give a project migration a template revision as its parent; use `depends_on` when it needs a template table.
- Every schema change is an Alembic migration (`make migration name="..."`), reviewed by hand: autogenerate misses renames, extensions and some constraints, and a migration says what happens to existing rows. `alembic check` runs in the tests, so a model without a migration fails `make check`.
- Database tests use the `db_session` or `db_client` fixtures: a real PostgreSQL with pgvector (testcontainers, or `TEST_DATABASE_URL`), rolled back after each test. Never mock the database.
- Files: object storage over the S3 API (`app/storage.py`; R2 in production, RustFS locally with `make storage-up`). Inject `StorageDep`; let browsers upload with `presigned_put(key, content_type=..., size=...)` (type from `STORAGE_UPLOAD_TYPES`, size up to `STORAGE_MAX_UPLOAD_BYTES`, both signed) and download with `presigned_get` (always an attachment), so file bodies don't pass through the API. Request bodies over `MAX_REQUEST_BYTES` (1 MiB) get a 413. Build keys from ids the server chooses, never from user-supplied names. Storage tests use the `storage_settings` fixture: a real RustFS, a fresh bucket per test. Never mock storage.
- Language models only through the gateway: inject `app.llm.gateway.GatewayDep` and call `gateway.model()`; embeddings through `gateway.embeddings()` (`await ...aembed_documents(texts, feature=...)`), under the same budget. Only `app/llm/` may import `langchain` or a provider SDK (`lint-imports` enforces it); never build a model elsewhere or pass a `"provider:model"` string to LangChain, because that skips the budget. `langchain_core` (messages, runnables) is fine anywhere.
- Always await model calls (`ainvoke`, `astream`, `abatch`): the budget can't stop a synchronous `invoke()`. Keep one event loop per process (a worker runs one loop for all its jobs, never `asyncio.run()` per job): the provider integrations cache HTTP connections tied to the first loop. A call the daily budget can't cover is refused with a 503 before it is sent; every call gets an `llm_call` row with its real cost. Send text and images only: the budget can't bound documents, audio or video, so a call carrying them is refused. Calls that would be billed beyond tokens are refused too: a tool the provider runs (web search, file search, code execution) or a dearer service tier (priority); give the model a tool the app runs instead, or add those prices first.
- Reservations a crashed process left open count against the day at their reserved cost; `make llm-report` reports any older than 30 minutes, and `python -m app.llm.report --expire-stale` (or a scheduled job calling `expire_stale`) closes them. Prompts past a price's `max_prompt_tokens` (OpenAI: 272K) are refused with a 422 rather than under-recorded.
- Tag model calls with what they're for and whom for: `config=gateway.call_config(user, "answer", prompt)`. With `LLM_USER_DAILY_BUDGET_USD` set, each user's calls are capped per day (429 when used up) as well as the global budget (503); set it whenever users can trigger model calls. `feature` is a short fixed name; `user_ref` an opaque id, never a name or email. Every call's tokens (reasoning and cache included), cost and latency land in `llm_call`; `make llm-report` sums them by day, model, prompt or feature, and a log warns once a day at 80% of the budget.
- Observability: FastAPI's native OpenTelemetry traces requests (not `/health`), records HTTP metrics and logs unhandled exceptions; the gateway adds `llm.calls`, `llm.tokens`, `llm.cost` and `llm.latency`. Nothing is exported until the `OTEL_*` settings in `.env.example` are set. Keep metric labels to bounded sets (no user ids).
- A new model needs its prices in `app/llm/prices.py` (embedding models in `EMBEDDING_PRICES`) (integer micro-USD per million tokens, from the provider's pricing page, with the date checked) before `LLM_MODEL` names it; the gateway refuses to start otherwise.
- Prompts are Markdown files in `app/prompts/`, loaded with `load_prompt(name)` and sent with `config=prompt.config()` so each call records the prompt's version. Never fetch prompts at runtime.
- Agents stop after `AGENT_MAX_STEPS` steps (default 25; 422 to the caller). Derive or check every `thread_id` server-side against the current user (e.g. `f"{user.id}:{conversation_id}"` after confirming they own the conversation): a caller-supplied thread id would let one user read another's thread.
- Agents: `gateway.agent(tools, system_prompt=...)` builds LangChain's `create_agent` on the gateway's model with the Postgres checkpointer; pass a `thread_id` in `configurable`. For more than a plain tool loop, build a LangGraph `StateGraph` whose nodes call `gateway.model()` and compile it with `checkpointer=gateway.checkpointer`. A test fails on any `create_agent`/`init_chat_model` given a model string. The checkpoint tables come from Alembic (`app/llm/checkpoints.py`); when a langgraph-checkpoint-postgres upgrade adds a migration, a test says so: add a revision that calls `checkpoints.apply_migrations` inside `autocommit_block()`.
- Evals live in `tests/evals/`, marked `eval` and `langsmith`, and run only with `make eval` (capped budget; uploaded to LangSmith when `LANGSMITH_API_KEY` is set). `test_gateway_evals.py` checks the gateway itself against the real provider (real cost settled, streamed usage, structured output, an agent's tool loop, the budget refusing); put the product's evals in their own files beside it. Log inputs, outputs, reference outputs and feedback with `langsmith.testing`; assert only what must hold for a release.
- Keys for `make record-llm` and `make eval` come from the shell or `backend/.env` (git-ignored; never commit a key or paste one into a command). The tests themselves never read `backend/.env`.
- Tests never call a model: mark a test that does `@pytest.mark.vcr` and `@pytest.mark.block_network`, and it replays `tests/cassettes/`. Record with `make record-llm` (real key, capped spend), check the cassette holds no secrets or personal data, and commit it. Test budget logic with LangChain's fake chat models.
- Tests are async (`pytestmark = pytest.mark.anyio`) and drive the app in-process through the `client` fixture; a bug fix comes with a test that fails without it.
- The image (`backend/Dockerfile`, `make image`; `make up` runs it with the database) installs the app from the lockfile into a virtualenv and runs it as UID 10001 with uvicorn, one process per container. On SIGTERM it finishes requests for `UVICORN_TIMEOUT_GRACEFUL_SHUTDOWN` (25 s): keep that under the platform's grace period. Set `FORWARDED_ALLOW_IPS` to the load balancer's addresses so client IPs and the scheme are right. Migrations never run at start-up: the `migrate` service locally, and a one-off job with the same image and `alembic upgrade heads` before each rollout. Deploy by the digest the publish workflow outputs, never a tag. Keep secrets out of the image (`.dockerignore`) and pass them as environment variables.
- Dependencies: add to `backend/pyproject.toml`, run `make lock`, commit both files. FastAPI stays pinned to one minor (`<0.N+1`) because 0.x minors can break.
