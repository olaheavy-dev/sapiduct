# Frontend (Next.js)

Owned by house-template-nextjs. Sources: the Next.js docs bundled with the installed version (`frontend/node_modules/next/dist/docs/`; see `frontend/AGENTS.md`), React (https://react.dev), Tailwind CSS (https://tailwindcss.com/docs) and pnpm (https://pnpm.io).

- Read the version-matched docs in `frontend/node_modules/next/dist/docs/` before using a Next.js API: this is Next.js 16, and training data is often older (no `next lint`, `proxy.ts` instead of `middleware.ts`, Cache Components). `next dev` keeps a managed block in `frontend/AGENTS.md`; commit it when it changes.
- While `next dev` runs, read its state rather than guessing: the Next.js DevTools MCP server (`next-devtools` in the root `.mcp.json`) talks to the dev server's own MCP endpoint, `/_next/mcp`, which reports its routes, server logs and compilation issues. Browser console errors also appear in the `next dev` terminal. If a dev server is already running, use it (`.next/dev/lock` holds its URL) rather than starting another.
- App Router under `frontend/src/app/`; Server Components by default, `"use client"` only where a component needs state, effects or browser APIs. Cache Components is on: wrap request-time data in `<Suspense>` and mark cached work with `"use cache"`.
- Styling is Tailwind v4 over the semantic tokens in `src/styles/tokens.css` (`bg-bg-secondary`, `text-text-primary`, `border-border-primary`...). Never hard-code colours, radii or fonts in components; re-skin by changing token values, and keep every text colour at 4.5:1 or more on every background (the template's tests check the starter set).
- Accessible by default: one `h1` per page, real buttons and links, labels on every input, visible focus (`:focus-visible` uses the focus-ring token), and nothing that only works on hover.
- Dependencies: pnpm 12 on Node 26 (`.node-version`). Add with `pnpm --dir frontend add <pkg>` (exact versions are saved), run `make lock-frontend`, commit both files. Install scripts run only for packages allowed in `frontend/pnpm-workspace.yaml`.
- Checks: `make check` runs ESLint (no warnings allowed), Prettier, `tsc` with strict settings, Vitest and a production build. Unit-test components with Testing Library by role and text, as a user would find them.
- Never put secrets in `NEXT_PUBLIC_*` variables: they are written into the browser bundle at build time. Server-only code reads plain environment variables.
- Security headers: `next.config.ts` (`SECURITY_HEADERS`) puts nosniff, frame-deny, no-referrer, COOP, a Permissions-Policy and (production) HSTS on every response; `src/proxy.ts` sets the Content Security Policy from `src/lib/csp.ts` per request. Prerendered pages get `script-src 'self' 'unsafe-inline'` (no scripts from other origins); a page that shows sensitive data (account, billing, admin) goes in `NONCE_PATHS`, gets a per-request nonce with `'strict-dynamic'`, and must render per request: `export const instant = false` and `await connection()` before anything else. No inline event-handler strings, `eval` or scripts from other origins; an origin the browser must call (the object store for uploads) goes in `CSP_CONNECT_SRC`, read at request time.
- Errors: `not-found.tsx` (call `notFound()` for a missing record), `error.tsx` and `global-error.tsx` show a fixed message, a retry button and the error's digest (the id the server logged it under); never render an error's message.
- End-to-end tests: Playwright in `frontend/e2e/` against the production build on the standalone server, in light, dark and a phone's width. Add every new page to `PAGES` in `e2e/pages.spec.ts`: each must pass axe (WCAG 2.2 AA), cause no CSP violation or page error, have one `h1`, and match its screenshot in `e2e/screenshots/`. Write journeys by role and text, as a user would. `make check` runs them; `make e2e-frontend` alone.
- Screenshots are compared only in Playwright's Linux image (Docker), where every machine renders the same pixels: CI always, locally with `E2E_DOCKER=1`; a plain local run skips them. After a page or a token changes on purpose, run `make screenshots-frontend`, look at each changed image, and commit them with the change. Never make them any other way.
- The image: `frontend/Dockerfile` builds the standalone server and runs it as a non-root user with `node server.js`; it reads every setting (`API_BASE_URL`, `CSP_CONNECT_SRC`) at request time, so one image goes through every environment, and it stops gracefully on SIGTERM. `/health/live` is its liveness check (it never calls the backend). `make up-frontend` runs it through `frontend/compose.yaml`; every push to main that touches `frontend/` publishes it (`.github/workflows/publish-web.yml`), and a deploy uses that run's digest, never a tag.
- Talking to the backend: Client Components use `api` from `@/lib/api/browser`, which calls the frontend's own `/api/*` proxy (`src/app/api/[...path]/route.ts`); Server Components, Server Actions and Route Handlers use `await serverApi()` from `@/lib/api/server`, which calls `API_BASE_URL` directly. Both are typed by `src/lib/api/schema.d.ts`: `const { data, error } = await api.GET("/v1/me")`, and handle `error` (an RFC 9457 problem). Never call the backend's URL from the browser, and never give the browser its credentials.
- `src/lib/api/schema.d.ts` is generated from the backend's OpenAPI schema: never edit it by hand. After changing the backend's routes or models, run `make api-types` and commit the result; `make check` fails while it is behind.
- Sign-in: `backendCredentials` in `src/lib/auth.ts` is the one function to replace with the project's provider. It reads the frontend's session from the request and returns the headers that prove the user to the backend (usually a bearer token); the proxy and `serverApi()` attach them server-side and pass nothing of the browser's own cookies or Authorization on. It fails closed: in production nobody is signed in until it is replaced, and `DEV_USER` (development only) stands in for a user through the backend's `X-Dev-User` header.
- Environment: `API_BASE_URL` and `DEV_USER` go in `frontend/.env.local` (copy `frontend/.env.example`); both are read at request time, so one build runs in every environment. The proxy answers 503 when `API_BASE_URL` is unset, 502 when the backend can't be reached and 504 after 60 s.
